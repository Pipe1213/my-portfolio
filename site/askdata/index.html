What it does

You ask a question in plain English and get a sentence with the names and numbers that matter, a chart or a table you can copy or download as CSV, and the SQL behind it. It handles follow-ups in the same conversation (“now only the top 5”), keeps past conversations, lets you browse the tables, and connects to your own PostgreSQL database through a read-only user.

It is built for people who know their business but don’t read SQL. They can’t check the query, so the app has to decide when to answer at all.

Answer, clarify or decline

A triage call sees the question, the conversation and the candidate tables, and returns one of three decisions. It answers by default and states small choices as assumptions. It asks only when two readings would give materially different answers, and declines only when no column could hold the fact.

How a question is answered

  1. Schema. At startup the backend reads tables, columns, types, keys and comments. Partitioned tables appear as one table, so the model can’t sum two monthly partitions and call it the total.
  2. Triage. One model call decides to answer, clarify or decline.
  3. Retrieval. Tables and columns are scored by the words in the question through a small business vocabulary (“spent” → amount, payment), plus the shortest foreign-key path between matched tables, so the model sees the joins it needs.
  4. SQL. One call writes a single SELECT and up to three assumptions in plain words; a second call reviews it against the question and can ask for one rewrite.
  5. Checks and run. sqlglot parses the query and allows one read-only SELECT. It runs in a read-only transaction with a 10-second timeout and a 200-row cap; errors go back to the model for a bounded repair.
  6. Answer. A small model writes the sentence from the result rows. Every number in it is checked against the rows, and a plain template replaces it if one doesn’t match.

Four of these steps call a model, each with one narrow job and a structured (Pydantic) output; the rest is plain Python. There is no agent loop, so the number of model calls per question, and with it the cost and the latency, has a fixed upper bound.

Results

I tested it on 52 questions about two demo databases, including questions that are vague on purpose and questions the data can’t answer. Each answer was checked against the result of a hand-written SQL query.

Safety

AskData is meant to be pointed at databases it doesn’t own, so it doesn’t rely on a single check.

  • Before connecting, it inspects the database user and refuses it, with the reasons, if it is a superuser, can create objects, can change any table, or can read or write server files.
  • The SQL must be one SELECT; COPY and risky functions such as pg_read_file, pg_sleep and dblink are denied anywhere in the query.
  • Every query runs in a read-only transaction with a 10-second timeout and at most 200 rows.
  • Connections added in the interface live in memory only, and passwords are masked in logs.

Limits

  • Tested on two small demo databases and 52 questions; a difference of one or two questions is within run-to-run noise.
  • One model family (OpenAI). Answers vary a little between runs.
  • An answer takes about 8–9 seconds (median), because it needs four model calls.
  • The number check catches invented numbers, not a correct number attached to the wrong name.
